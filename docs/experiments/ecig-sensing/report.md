# 센싱 가능 전자담배 자동 수집 — 실험 설계와 시뮬레이션 결과 (NonsmokingNote)

작성 2026-10-21 · 코드 `sim.py` · `sensitivity.py` · 결과 `results.json` · `results.txt` · `sensitivity.txt`

> **먼저 읽어 주세요.** 이 문서의 모든 수치는 **가정한 생성 모형 위에서 돌린 시뮬레이션의 출력**입니다. 실기기를 측정한 값이 아닙니다.
> 가정은 §2 에 모았고 전부 **문헌·실측으로 보정하기 전**입니다. 그래서 절대값(“recall 0.92”)이 아니라 **설계 선택지끼리의 상대 비교**와 **어떤 가정이 결과를 좌우하는가**를 읽는 용도입니다.
> 이전 대화의 실험 1~3 코드는 제가 볼 수 없었고, 붙여 주신 수치(스캔 recall 0.97 · 2단계 precision 1.000 · 완전성 95 % 기준)만 §5 에서 대조했습니다.

## 1. 목적과 가설

센싱이 가능한 전자담배에서 사용자 개입 없이 퍼프 데이터를 모아 `puff_log` 에 쌓고, 퍼프·니코틴 추세로 중재 메시지를 보내는 흐름(기기 찾기 → 센싱 확인 → 연결 → 액상 농도 입력 → 자동 수집)이 **설계대로 동작할 조건**을 정한다.

| 가설 | 합격 기준(사전 정의) |
|---|---|
| H1 5 s BLE 스캔으로 본인 기기를 찾는다 | 끝-끝 recall ≥ 0.95 (단일 기기 가정 환경) |
| H2 2단계 판별이 센싱 오표시를 없앤다 | 2단계 precision ≥ 0.99 · 1단계 대비 개선 |
| H3 기기 링버퍼 + 재동기화로 하루 완전성이 높다 | 평균 ≥ 0.99, 하위 5 % ≥ 0.95 |
| H4 앱의 완전성(%) 표시가 실제와 맞는다 | 앱을 여는 임의 시각에서 과대표시 > 5 %p 인 비율 ≤ 5 % |
| H5 퍼프 길이 정보가 니코틴 추정을 개선한다 | ±25 % 안 비율 +10 %p 이상 |
| H6 전주 대비 추세 메시지가 신뢰할 만하다 | 실제 변화 0 일 때 거짓경보 ≤ 5 % · 실제 20 % 감소 검출 ≥ 80 % |

## 3. 실험 설계와 코드 구조

`sim.py` 는 표준 라이브러리만 씁니다(`python3 sim.py`, 약 1 분, 시드 고정). 실기기 치환 지점은 굵게 표시했습니다.

| 실험 | 함수 | 하는 일 | 실기기로 바꿀 곳 |
|---|---|---|---|
| 1 탐색·판별 | `exp1_trial` | 주변 기기 생성 → 광고 수신 확률(RSSI·듀티) → 1단계 필터(서비스 UUID · 제조사 ID 표) → 신호 상위 k 대 **GATT 연결·서비스 확인** | **`heard()` = 실제 BLE 스캔 결과**, **GATT 확인 = `connect()` + `discoverServices()`** |
| 2 수집 완전성 | `exp2_day` · `gen_disconnects` | 하루 퍼프 + 끊김 구간(멀어짐·무선·OS 중지) → 실시간만 / 링버퍼 K / 카운터형 세 방식의 도착 여부 · 시각 오차 · 앱이 아는 완전성 | **`gen_day_puffs` = 기기 로그**, **`gen_disconnects` = 앱 연결 로그** |
| 3 니코틴·추세 | `nicotine_day` · `exp3_trend` | 진짜 니코틴 vs 추정기 3종(E1 퍼프 수 / E2 기기 길이 / E3 2 Hz 스트림 길이), 2주 비교 검출 | **진짜값 = 액상 무게 감소(저울 0.001 g)** |

지표: recall · precision · 완전성(도착/발생) · 앱 표시 완전성과 진짜 완전성의 차 · |상대오차| · 거짓경보/검출률. 민감도는 `sensitivity.py`.

## 4. 결과

### 4-1. 실험 1 — 탐색·판별 (시행 3,000 회/칸)

단계별 recall 은 같은 시행의 누적입니다(수신 → 후보 필터 통과 → 상위 3대 안 → 센싱 확인).

| 환경 | 스캔 | 수신 | 후보 | 상위3 | **최종** | precision 1단계 | precision 2단계 |
|---|---|---|---|---|---|---|---|
| 집 | 3 s | 0.885 | 0.852 | 0.852 | 0.847 | 0.851 | 1.000 |
| 집 | **5 s** | **0.964** | 0.930 | 0.930 | **0.925** | 0.866 | 1.000 |
| 집 | 10 s | 0.998 | 0.956 | 0.956 | 0.950 | 0.859 | 1.000 |
| 카페 | **5 s** | 0.970 | 0.926 | 0.924 | **0.919** | 0.608 | 1.000 |
| 다중 전자담배 | **5 s** | 0.968 | 0.933 | 0.852 | **0.848** | 0.715 | 1.000 |
| 다중 전자담배 | 10 s | 0.996 | 0.955 | 0.870 | 0.863 | 0.721 | 1.000 |

**해석**
- 5 s 면 수신은 0.96~0.97 이고 8 s 이상은 +0.03 뿐입니다. **스캔을 늘려 얻는 것은 작습니다.**
- 끝-끝 손실은 대부분 두 곳에서 납니다. ① **후보 필터**(수신 0.964 → 후보 0.930): UUID 를 숨기는 `sensing_mfgonly` 기기가 제조사 표에 없으면 놓침. ② **상위 3대 제한**(다중 전자담배 환경에서 후보 0.933 → 상위3 0.852).
- **H1 부분 기각**: 수신만 보면 합격, 끝-끝은 0.85~0.93 이라 기준 0.95 에 못 미침. **H2 방향 지지**: 1단계만으로 라벨하면 precision 0.61~0.87, 카페처럼 타인의 같은 제조사 기기가 있으면 가장 나쁨.
- **precision 2단계 1.000 은 설계상 자명한 값**입니다(서비스가 있는 기기만 통과시키므로 오탐 불가). 실제 위험은 *서비스는 보이나 데이터가 안 나오는* 경우(인증·펌웨어)이며 이 시뮬레이션은 그것을 재지 못합니다 → §6 “퍼프 1회 시험” 단계.

**민감도 (집, 5 s, `sensitivity.txt`)**

| 바꾼 가정 | 값 | 수신 | 최종 |
|---|---|---|---|
| 스캔 듀티 | 0.25 / 0.5 / 1.0 | 0.80 / 0.96 / 1.00 | 0.76 / 0.92 / 0.95 |
| 제조사 표 포괄율 | 0.6 / 0.8 / 0.9 / 1.0 | 0.96~0.97 | **0.80 / 0.88 / 0.92 / 0.96** |
| 전자담배 광고 간격 | 0.1 / 0.5 / 1.0 / 1.28 / 2.0 s | 1.00 / 1.00 / 0.98 / 0.93 / 0.82 | 0.97 / 0.95 / 0.93 / 0.88 / 0.78 |
| 경로손실 지수 · 가림 편차 | 2.0~3.0 · 4~9 dB | 0.96~0.97 | 0.91~0.93 (거의 무관) |
| 상위 k (다중 환경) | 1 / 3 / 5 / 8 | — | 0.54 / 0.85 / 0.91 / 0.93 |

**지배 요인은 무선 환경이 아니라 ① 스캔 듀티 ② 기기의 광고 간격 ③ 제조사 표 포괄율 ④ 상위 k** 입니다(대상이 0.3~3 m 로 가까워 신호 모형 가정에는 둔감). 즉 “5 s” 라는 숫자는 *이 가정의 듀티·광고 간격에서만* 성립합니다.

### 4-2. 실험 2 — 자동 수집 완전성 (일 1,500 건/구성)

| 구성 (OS 가 앱을 멈추는 폰) | 자정 완전성 평균 | 하위 5 % | 재동기화 뒤 | 시각 오차 p99 |
|---|---|---|---|---|
| 실시간만(기기 저장 없음) | 0.801 | 0.576 | 0.801 | — |
| 링버퍼 16건 | 0.974 | 0.871 | 0.975 | 0.68 s |
| 링버퍼 64건 | 0.998 | 1.000 | 1.000 | 0.95 s |
| 링버퍼 256건 | 0.999 | 1.000 | 1.000 | 1.11 s |
| 카운터형(개수만) | 0.998 | 1.000 | 1.000 | — |

포그라운드 서비스를 유지하는 폰은 실시간만 0.827, 나머지는 거의 같습니다. **OS 의 앱 중지는 실시간만 방식에서도 2.6 %p 정도**로, 가장 큰 손실원은 “폰에서 멀어짐”입니다.

- **H3**: 링버퍼 64건 이상은 합격, **16건은 기각**(하위 5 % 0.87). 기기에 저장 능력이 없으면 하루 약 20 % 를 잃습니다.
- 시각 오차(기기 시계 편차 ±80 ppm 가정)는 재동기화 시 1 초 안쪽 — 문제 아님. **다만 기기가 전원 꺼짐으로 시계를 잃는 경우는 모형에 없음**(큰 오차가 날 수 있는 실제 위험).
- **H4 기각 (끊김 중)**: 하루 중 임의 시각 1,475 번 스냅샷에서, 앱이 받은 일련번호로 계산한 완전성이 실제보다 평균 +1.6 %p, p95 +11.6 %p 과대. 스냅샷의 **19 %가 끊겨 있는 중**이었고 그중 **39 %** 가 5 %p 넘게 과대표시. 이유: 끊긴 동안 생긴 퍼프는 일련번호 *뒤쪽*에 있어 앱이 존재를 모릅니다. → **끊긴 중에는 %를 보이지 말고 “동기화 대기 · 마지막 동기화 hh:mm”** 로.
- **카운터형 기기**(누적 카운터만 주는 IQOS 류 가정): 개수 완전성은 높지만(0.998) **시각을 모릅니다.** 연결 중 읽기 간격 1~5 s 이면 개수 오차 −0.1~−0.2 %, **30 s 이면 −18 %**(20 s 간격 퍼프가 합쳐짐). 시간대(1 h)별 절대오차는 **17 %**(끊긴 구간 퍼프를 재연결 시각에 몰아 배정하기 때문). 야간 흡연 구간 표시 같은 시각 기능은 제한적이고, 퍼프 길이가 없어 **니코틴 추정은 불가**(퍼프 수까지만).
- 퍼프 길이를 2 Hz 로 재면 한 퍼프당 상대오차 평균 5.9 %(p95 15.5 %) — 양자화 오차는 하루 합에서 상쇄됩니다(§4-3).

### 4-3. 실험 3 — 니코틴 환산과 추세 검출

**일 합계 정확도**(600 명 × 7 일)

| 추정기 | |오차| 중앙값 | p90 | ±25 % 안 |
|---|---|---|---|
| E1 퍼프 수 × 고정 평균 | 21.6 % | 47.4 % | 58.4 % |
| E2 기기가 보낸 퍼프 길이 | 12.8 % | 30.7 % | 82.2 % |
| E3 2 Hz 스트림에서 잰 길이 | 12.9 % | 30.6 % | 82.3 % |

H5 지지. **E3 ≈ E2** → 기기가 길이를 요약해 주지 않아도 2 Hz 스트림이면 충분하고, **유휴 0.1 Hz 는 퍼프 길이 추정에 영향이 없음**(길이는 퍼프 중 샘플로 재므로). 남는 오차는 사용자별 액상 소비율(σ 0.20)과 퍼프마다 변동(σ 0.30)입니다. **이 추정기는 모집단의 진짜 평균 소비율을 안다고 가정**하므로 실제 오차는 더 큽니다(낙관적).

| B | 0.95 · 0.80 | **예** | 0.183 | 0.872 | 0.018 | 0.508 |
| B | 0.85 · 0.70 | 아니오 / 예 | 0.747 / 0.147 | 0.988 / 0.838 | 0.377 / 0.015 | 0.915 / 0.490 |

- 퍼프가 생기는 과정 자체의 주간 변동(비율 표준편차 ≈ 0.10)이 커서, 완전성이 **100 % 라도 10 % 문턱 거짓경보가 13 %** 입니다. **H6 기각**(거짓경보 ≤ 5 % 와 검출 ≥ 80 % 를 동시에 만족하는 문턱이 없음: 10 % 문턱은 검출 0.84 / 거짓 0.13, 20 % 문턱은 거짓 0.01 / 검출 0.49).
- 완전성이 *무작위로* 낮은 것(시나리오 A)은 추세에 거의 영향이 없습니다. **위험은 두 주 사이에 완전성이 체계적으로 바뀔 때(B)** — 폰 설정 변경, 기기 교체, 앱 업데이트 — 이때 미보정 추세는 감소로 보고 **거짓경보 72~75 %** 입니다. 일련번호 기반 완전성으로 나누어 보정하면 15~18 % 로 내려갑니다.
- 단, 보정에 쓰는 완전성이 정확해야 합니다 → **주간 리포트는 마지막 동기화가 끝난 뒤(예: 다음 날) 계산**하고 끊긴 중에는 만들지 않기(H4 결과와 연결).
- 비율 변동 0.10 은 **제가 만든 퍼프 생성 과정의 산물**이며 실제 사용자 변동이 아닙니다. 공개 토포그래피·장기 자료로 보정해야 할 **가장 중요한 가정**입니다.

## 5. 이전 대화 수치와의 대조

| 이전 대화 | 이 시뮬레이션 | 판단 |
|---|---|---|
| “5 s 스캔 recall 0.97” | **수신 단계 0.964(집) · 0.970(카페) · 0.968(다중)** | 같은 정의(스캔에서 보이는가)라면 일치. 다만 이 일치는 **가정(듀티 0.5, 광고 1 s 안팎)에서만** 나오고 듀티 0.25 면 0.80 |
| “2단계 precision 1.000” | 2단계 1.000, 1단계 0.61~0.87 | **1.000 은 정의상**. 의미 있는 비교는 1단계 대비 개선 |
| “수집 완전성 95 % 미만이면 ‘기기를 가까이 두세요’” | 링버퍼 64건이면 재동기화 뒤 완전성 ≈ 1.0 | 안내가 **작동해야 하는 상황**은 링버퍼가 작거나 없을 때. 끊긴 중 표시값은 과대(H4) |
| “퍼프 중 2 Hz / 유휴 0.1 Hz” | 퍼프 길이 오차 5.9 % → 일 합에서는 상쇄 | 이 절약 설정은 **추정 정확도에 영향 없음**(가정: 유휴 중 퍼프 감지는 기기 인터럽트가 하고 BLE 전송만 0.1 Hz) |

## 6. 설계에 주는 시사점 (시뮬레이션 안의 근거)

| 결정 | 제안 | 근거 | 확신 |
|---|---|---|---|

## 7. 실기기 검증 계획 (시뮬레이션을 대체할 측정)

| 실험 | 측정 | 진짜값(ground truth) | 표본 | 합격 |
|---|---|---|---|---|
| 1 | 환경 3종 × 스캔 1~10 s, 폰 기종 ≥ 3 | 사용자가 “내 기기” 확인 | 조건당 ≥ 200 회(95 % 신뢰구간 ±3 %p) | 끝-끝 recall ≥ 0.95 |
| 2 | 7~14 일 자유 사용 | 기기 일련번호(링버퍼 포함) + 사용자 수기 버튼 | 기기 ≥ 10 대 · 14 일 | 평균 ≥ 0.99, 끊긴 중 표시 과대 ≤ 5 %p 인 비율 ≥ 95 % |
| 3 | 액상 탱크 무게 전후(0.001 g 저울) + 퍼프 길이 합 | **액상 질량 감소 → mg 니코틴** | 사용자 ≥ 20 · 7 일 | 일 합 ±25 % 안 비율, 소비율 보정 필요 여부 |

기기 후보로 이전 대화에서 오픈소스 센서(PuffPacket)와 일부 상용 기기의 비공식 BLE 분석 저장소가 언급되었으나, **이번 작업에서 그 저장소·논문·프로토콜을 직접 확인하지 못했습니다.** 실제 기기 선정 전에 라이선스·사양을 먼저 확인하세요.

## 8. 한계와 위험

- **모형이 곧 결과**: 퍼프 과정(§2)과 링크 과정은 제가 가정한 것이라, 특히 H6 의 “주간 변동 0.10”, H3 의 끊김 빈도는 실제와 크게 다를 수 있습니다. 민감도 분석은 실험 1 에만 했습니다.
- **상관 없음**: 끊김과 퍼프를 독립으로 두었습니다. 실제로는 “폰을 두고 나가서 피우는” 상관이 있어 실시간만 방식의 손실이 더 클 수 있습니다.
- **연결 모형 단순화**: 스캔 스로틀링, 폰 기종별 BLE 스택, 보안 연결(페어링) 실패, 기기 전원 꺼짐·시계 초기화는 모형에 없습니다.
- **니코틴 수치의 의미**: 기화 액상의 니코틴 함량이며 흡수량이 아닙니다. 화면·알림에 “흡수량”으로 읽히는 표현을 쓰지 마세요. 식약처 웰니스 판단 경계(표시된 사용목적으로 가름)에 걸릴 수 있어 문구는 검토가 필요합니다.
- **개인정보**: 퍼프·시각·장소(스캔 환경)는 건강 정보입니다. Supabase 저장 위치·동의·약사 공유 동의 범위를 문서화하고, “서버로 보내지 않는다” 류의 표현은 쓰지 마세요.
- **기기 접근**: 제조사 앱 프로토콜을 분석하는 일은 약관·법적 검토와 IRB 문서 명시가 필요합니다(연구 목적 한정). 인증 핸드셰이크가 있는 기기는 우회하지 말고 외부 센서 방식으로 전환하세요.
