# 연구형 앱 · 5단계 「연결」 (2026-11-13 · 제안 · 앱에 반영 안 됨)

4단계 결론(첫 연구는 새 하드웨어 없이, 센서 어댑터는 `manual` 과 `fake` 먼저)을 받아, **연결 메뉴가 무엇을 보여 주고 무엇을 점검하는지**를 정합니다. 이 단계도 **코드 없음 · 앱 동작 변경 없음 · 데이터가 기기 밖으로 나가는 길 없음**입니다. 실제 기기 연결과 전송은 켜지 않습니다(IRB·동의 문구 전).

## 2. 설계 제안 — 계약을 새로 만들지 않는다

`docs/RESEARCH-APP.md` 3절은 센서 어댑터를 `connect() · read() · status()` 로 적었습니다. 그런데 **이미 시험을 통과한 계약**이 있고 모양이 다릅니다:

```
provider = { id, name, capabilities:{seq, duration, ringBuffer},
             connect(), disconnect(), onPuff(cb), onLink(cb), readSince(seq) }
```

- **제안: `core/sensors/` 는 위 계약을 그대로 채택**하고 RESEARCH-APP.md 3절의 한 줄을 고칩니다(문서만).
- `capabilities` 가 곧 「이 기기가 무엇을 내주나」를 말한다 — `seq` 가 없으면 완전성을 잴 수 없고, 길이(`d`)가 없으면 니코틴 추정을 하지 않는 규칙이 이미 들어 있다. 연결 메뉴는 이 표시를 그대로 그린다.
- `manual`(옮겨 적기) 어댑터는 같은 계약으로 `capabilities:{seq:false,duration:false,ringBuffer:false}` 이고 `connect()` 는 즉시 성공, `onPuff` 대신 사용자의 입력을 받는 모양이다.

## 3. 연결 메뉴가 보여 줄 상태

| 상태 | 뜻 | 화면 문구(초안 · 문구는 확인 뒤 확정) |
|---|---|---|
| 연결 안 함 | 기기 없이 직접 기록하는 연구 참여 | 「기기 없이 직접 기록해요」 |
| 시험 중 | `fake`(가짜 기기)로 점검 중 | 「시험용 가짜 기기예요 — 실제 값이 아닙니다」 |
| 연결됨 / 끊김 | `onLink` 상태 | 연결 시각 · 마지막으로 받은 시각 |
| 빠진 구간 있음 | `seq` 에 구멍 | 「N건 빠졌어요」(숫자만, 원인 추측 안 함) |
| 지원 안 함 | 이 브라우저에서 블루투스 없음(iOS 사파리 등) | 「이 기기에서는 연결할 수 없어요」 |

**짚어 둘 것**
- 「빠졌다」는 숫자로만 말합니다. **왜 빠졌는지·건강상 의미는 말하지 않습니다**(「위험 알람」·「모니터링」류 문구 금지).
- 퍼프 시각은 **받은 시각**입니다(기기 시계를 모름). 끊겼다 다시 연결해 한꺼번에 받은 것은 시각이 틀립니다 — 화면에 한 줄 표시합니다.
- 연구 모드에서도 **연결 화면 자체는 기본으로 감춰 둡니다**(전송 어댑터와 같은 규칙).

## 4. 가짜 기기로 점검할 시나리오 (연결 메뉴의 「점검」 버튼)

1. 정상 연속 수신 — 빠진 구간 0
2. 중간에 끊겼다 재연결 — `readSince` 로 채워지는지
3. 링버퍼가 넘쳐 일부 영구 손실 — 「N건 빠졌어요」 숫자가 맞는지
4. 일련번호가 처음으로 되돌아감(기기 초기화) — 중복·역행을 어떻게 처리하는지
5. 같은 일련번호가 두 번 옴 — 한 번만 세는지
6. 숫자가 아닌 값 · 음수 · 큰 값 — 거르는지(`validRecord`)

이 여섯은 **`puff-core.test.mjs` 가 어디까지 이미 덮는지 먼저 읽고**, 덮이지 않은 것만 시험을 더합니다(6단계 이후 코드 일).

## 5. 이 단계에서 켜지 않는 것

실제 기기 연결 · 기기 값 저장 · 서버 전송 · 연구실 시트로 보내기 · 새 권한 요청(Health Connect 혈압 등). 연결 상태는 **이 폰 안에서만** 보입니다.
