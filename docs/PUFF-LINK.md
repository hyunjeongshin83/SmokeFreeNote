# 퍼프 연동 뼈대 (2026-10-21)

센싱이 가능한 전자담배의 퍼프를 자동으로 모으는 흐름의 **뼈대**입니다. 실제 기기와는 아직 연결하지 않았고,
**앱 본체(`index.html`)에는 연결하지 않았습니다.** 실험 화면 `labs/puff-link/index.html` 에서만 돕니다.
근거와 가정은 `docs/experiments/ecig-sensing/report.md` — 그 수치는 모두 시뮬레이션이며 실기기 측정이 아닙니다.

## 1. 있는 것

| 파일 | 내용 |
|---|---|
| `labs/puff-link/puff-core.js` | 순수 로직. 합치기(일련번호 중복 제거) · 누락 구간 · 완전성 · 하루 요약 · 니코틴 참고치 · 전주 대비 추세 · 카운터형 기기 · 저장 · **가짜 기기** |
| `labs/puff-link/index.html` | 실험 화면. 가짜 기기 연결 · 21일치 가짜 기록 · 오늘 요약 · 수집 상태 · 최근 7일 |
| `tests/puff-core.test.mjs` | `node --test tests/puff-core.test.mjs` — 18개. 핵심 로직을 일부러 망가뜨려 시험이 실패하는 것까지 확인함 |

화면은 기존 색·크기 토큰만 씁니다. 390px · 320px · 글자 200% 에서 가로 넘침 없음, 터치 단추 44px 이상, axe 위반 0 (이 환경의 Chromium 기준).

## 2. 저장

- `localStorage` 키 **`smokefree.puffs.v1`** 한 곳. 기존 기록 키(`smokefree.v1`)는 읽지도 쓰지도 않습니다 (시험으로 확인).
- 서버로 보내지 않습니다. 외부 글꼴·스크립트도 부르지 않습니다 (화면 실행 중 바깥 요청 0 으로 확인).
- 하루 약 200건 기준 약 100일치(2만 건)까지 보관하고 오래된 것부터 버립니다.

## 3. 시뮬레이션에서 이어받은 설계 규칙

| 규칙 | 근거 (report.md) |
|---|---|
| 기록은 기기의 **일련번호(seq)** 로 중복 제거. 실시간으로 받은 것을 재동기화로 또 받아도 한 번만 | §4.2 |
| 완전성 = 받은 수 ÷ (최대 seq − 최소 seq + 1). **끊겨 있는 동안에는 숫자를 주지 않고 「동기화 대기」** | 끊긴 중 표시의 39 % 가 5 %p 넘게 과대 |
| 전주 대비는 **앞선 2주**와 견주되, 기간이 덜 찼으면 합계가 아니라 **추적한 날수로 나눈 하루 평균**으로 비교(분모는 기록을 시작한 날부터 지금까지 — 퍼프가 없던 날도 진짜 0 으로 셈). 문턱 **20 %**, 양쪽 5일 이상 추적 필요 | 10 % 문턱은 자연 변동만으로 거짓경보 13~19 % |
| 추세는 **일련번호 누락을 채워 넣어** 계산. 두 기간의 경계에 걸친 누락은 **시간에 비례해 나눔**(가정: 누락이 그 시간 동안 고르게 퍼짐 — 밤에는 틀릴 수 있어 작은 오차가 남음) | 주 사이 완전성이 바뀐 것을 변화로 오해(거짓경보 72 %)하지 않게 |
| 하루 안에 **길이를 아는 퍼프가 일부뿐이면** 니코틴 참고치를 보여 주지 않음 | 일부만으로 하루를 대표시키면 과소 표시 |
| **다시 연결하면 끊긴 동안 기기에 쌓인 기록을 가져온다**(실기기에서는 `readSince(마지막 seq)`). 연결 표시만 바꾸면 일련번호 맨 뒤의 꼬리는 빠진 줄 몰라 완전성이 100 % 로 나옴 | 시험: 꼬리 1건이 빠진 채 100 % |
| 퍼프 길이가 없는 기기(카운터형)는 니코틴 참고치를 만들지 않음 | §4.2 |
| 기기에 저장되는 퍼프는 **64건 이상** 을 권장 (16건은 하루 약 2.5 % 손실) | §4.2 |

## 4. 실기기를 붙일 때 맞춰야 할 모양 (`puff-core.js` 머리의 계약)

```
provider = { id, name, capabilities:{seq,duration,ringBuffer}, connect(), disconnect(),
             onPuff(cb({seq,t,d})), onLink(cb({connected})), readSince(seq) → Promise<[{seq,t,d}]> }
```

블루투스 코드는 **아직 넣지 않았습니다.** 기기의 서비스 UUID·데이터 형식이 정해져야 쓸 수 있고, 권한 요청 코드를
기기 없이 넣어 두면 검증할 수 없습니다. 안드로이드는 `BLUETOOTH_SCAN` · `BLUETOOTH_CONNECT` 권한과 네이티브 코드가 필요합니다.

## 5. 하지 않은 것 · 결정이 필요한 것

- **실제 기기 선택** — 연구용 센서인지 시판 기기인지, 그 기기의 데이터 형식. 사람이 정할 일입니다.
- **앱 본체에 넣기** — 홈 · 기록 · 통계 화면과 이 모듈을 어떻게 이을지는 손님이 보는 화면 변경이라 대표님 확인 대상입니다 (CLAUDE.md §2).
- **서버 저장 · 약사 공유** — 건강 데이터가 기기 밖으로 나가는 일이라 결정과 동의 설계가 먼저입니다.
- 화면 문구(추세 문장 포함)는 **시안**입니다. 판단·단정을 피하고 「참고치」를 밝혔을 뿐 확정 문구가 아닙니다.
- 니코틴 수치는 기화된 액상의 양입니다. 몸에 흡수된 양이 아닙니다.

## 6. 블루투스 연결 프로토타입 (2026-11-09 · 앱 본체에 연결 안 됨)

대표님 요청(2026-11-09): 하드웨어(IQOS 같은 전자담배 센싱)를 연결할 수 있는 코드만 먼저 프로토타입으로.

| 파일 | 내용 |
|---|---|
| `labs/puff-link/ble-provider.js` | 4절의 provider 계약을 Web Bluetooth 로 구현한 뼈대. UUID · 데이터 형식을 밖에서 받음. 서비스 탐색기(`explore`) 포함 |
| `labs/puff-link/ble.html` | 시험 화면 — UUID 를 적고 연결 → 알림으로 받은 퍼프를 `PuffCore.ingest` 로 합쳐 개수 표시 · 서비스 목록 보기 |
| `tests/puff-ble.test.mjs` | `node --test tests/puff-ble.test.mjs` — 9개. 형식 해석 · UUID 정리 · 가짜 `navigator.bluetooth` 로 연결·알림·끊김·실패 정리 · 일련번호 중복 제거 |

**한계 (분명히)**
- **IQOS 는 이 코드로 읽을 수 없습니다.** 서비스 UUID · 데이터 형식이 비공개이고(`docs/DEVICES.md`) 제조사 앱의 성인 인증·페어링이 앞에 있으며, 기기가 외부 연결을 받아 주는지도 확인되지 않았습니다. 이 코드는 **값을 아는 기기**용 뼈대입니다.
- 데이터 형식 두 가지(`seq32-dur16` · `seq32`)는 **가정**이고 실기기와 맞춰 본 적이 없습니다. 실기기가 정해지면 `FORMATS` 에 그 형식을 더하세요.
- 퍼프 시각은 **받은 시각**입니다(기기 시계를 모름). 끊겼다 다시 연결해 한꺼번에 받은 기록은 시각이 틀립니다. `readSince`(끊긴 동안 쌓인 기록 읽기)는 아직 없고 `ringBuffer:false` 입니다.
- Web Bluetooth 는 https(또는 localhost) · 사용자의 누르기 동작이 필요하고 크롬·엣지(안드로이드 포함)에서만 됩니다. iOS 사파리는 지원하지 않습니다. 안드로이드 셸(WebView)에서는 쓸 수 없습니다 — 네이티브 `BLUETOOTH_SCAN` · `BLUETOOTH_CONNECT` 코드가 따로 필요합니다 (`docs/NATIVE.md`).
- 받은 값은 화면 안(메모리)에만 있고 저장하지도 서버로 보내지도 않습니다. 앱 본체의 기록과 잇는 일은 대표님 확인 대상입니다(5절).
- 실제 블루투스 기기로는 이 환경에서 시험하지 못했습니다. 시험은 모두 가짜 기기로 했습니다.

**실기기를 붙이는 순서**: ① 기기의 서비스·특성 UUID 와 데이터 형식을 확보(제조사 문서 · 연구용 센서의 명세) → ② `ble.html` 의 「서비스 목록 보기」로 UUID 가 보이는지 확인 → ③ 맞는 형식을 `FORMATS` 에 추가 → ④ `ble.html` 에서 퍼프가 들어오는지 확인 → ⑤ (결정 후) 앱 본체 연결.

## 7. 아이코스 퍼프 수 읽기 — 앱 본체에 연결 (2026-11-11 · 대표님 요청)

대표님 요청(2026-11-11): 자신의 흡연 데이터를 읽도록 IQOS 센싱 코드를 금연노트에 넣기. 공개 역분석(okhsunrog/iqos, MIT)을 옮긴 프로토콜입니다.

| 파일 | 내용 |
|---|---|
| `iqos-ble.js` | Web Bluetooth 로 IQOS 코어 서비스에 연결 → 제어 특성에 「퍼프 수 읽기」 명령을 2초마다 쓰고 알림으로 받은 누적 퍼프 수(u16)의 **차이**를 알림 |
| `SmokeFree_app.html` | 기록 탭 「측정값 적어 두기」 카드의 「아이코스에서 퍼프 수 읽기 (실험)」 단추. 연결해 있는 동안 늘어난 수를 「퍼프·스틱」 칸에 **채우기만** 하고, 저장은 사용자가 「측정값 저장」을 눌러야 함 |
| `tests/iqos-ble.test.mjs` | 6개 — 프레임 해석(참조 저장소 모양) · 차이(돌아감·튀는 값) · 가짜 기기 연결 · 거부·미지원 |

**한계 (분명히)**
- **실기기로 확인하지 못했습니다.** 제조사가 공개한 규격이 아니며, 프레임 해석은 시험 값으로만 맞춰 봤습니다. 기기가 외부 연결을 받아 주는지, 제조사 앱 페어링이 먼저 필요한지도 모릅니다. 안 되면 화면에 「연결하지 못했어요」가 뜨고 손으로 적는 길이 그대로 남습니다.
- 기기는 **누적 퍼프 수만** 줍니다. 퍼프 길이·세기가 없어 니코틴 추정은 하지 않습니다. 처음 읽은 값은 기준값이라 퍼프로 세지 않고, 이후 늘어난 만큼만 셉니다.
- 크롬·엣지(안드로이드 포함)에서만 됩니다. iOS 사파리와 안드로이드 앱 셸(WebView)에서는 단추가 보이지 않습니다.
- 읽은 값은 사용자가 저장해야 `smokefree.v1` 의 측정값(kind `puffs`)이 됩니다. 서버로 보내지 않습니다.
- 「이번 주 퍼프·스틱」 칸에 채워지므로 한 번 읽은 값이 한 주 합계와 섞일 수 있습니다. 칸 문구·통계 연결은 눈에 보이는 변경이라 정하지 않았습니다.
